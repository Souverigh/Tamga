# Замер реальной точности Тамги

Инструмент, чтобы честно ответить на вопрос «а насколько точно оно распознаёт»
на твоих реальных документах — а не на ощущениях от нескольких ручных тестов.

Не заменяет UI и не трогает прод — вызывает ту же самую функцию распознавания
(`lib/recognize.js`), что и сайт, только напрямую из терминала, с твоим
`GEMINI_API_KEY`. Реальные вызовы к Gemini, реальные деньги/квота — как если
бы ты сам загрузил эти файлы на сайте.

## Как этим пользоваться

1. Собери 15–20 (или сколько есть) реальных фото документов разных типов —
   можно тестовые/свои, главное чтобы были фото, а не идеальные сканы, раз
   именно так люди будут пользоваться сайтом. Положи их в `eval/documents/`
   (эта папка в `.gitignore` — фото туда не попадут в git).

2. Скопируй `eval/ground-truth.example.json` в `eval/ground-truth.json`
   (тоже в `.gitignore` — там будут реальные ФИО/данные, коммитить нельзя).

3. Для каждого файла впиши в `ground-truth.json`, какой это тип документа
   (`docType`, точное значение из `DOC_TYPES` в `lib/docSchema.js`) и — если
   готов сверять руками — правильные значения полей (`fields` для карточных
   типов, `items` для табличных вроде накладной). Смотри примеры в
   `ground-truth.example.json`.

   Можно указать только `docType` без `fields` — тогда скрипт посчитает
   точность только классификации для этого документа, без полей.

4. Убедись, что `GEMINI_API_KEY` доступен скрипту — либо экспортируй его
   в терминале (`export GEMINI_API_KEY=...`), либо просто положи в `.env`
   в корне проекта (как для `vercel dev`) — скрипт сам его прочитает.

5. Запусти:
   ```
   npm run eval
   ```

## Что покажет отчёт

- Точность классификации: сколько документов определены как правильный тип,
  в целом и по каждому типу отдельно (легко увидеть, если конкретный тип
  вроде «Акт выполненных работ» проседает).
- Точность полей: среди документов с верно определённым типом — сколько
  полей/ячеек таблицы совпало с эталоном (посимвольное сравнение после
  тримминга пробелов).
- Список конкретных расхождений (какое поле, что ожидалось, что пришло) —
  чтобы было видно, штучная ли это ошибка или систематическая (например,
  модель всегда путает конкретный формат даты).

Каждый запуск также сохраняет полный отчёт в `eval/results/<дата>.json`
(тоже в `.gitignore`) — так можно сравнивать точность между сессиями и
видеть, реально ли помогают правки промптов, а не гадать.

## Важно понимать про эту метрику

- Это точность на ТВОЕЙ конкретной выборке документов — не абстрактная
  «точность Gemini». Чем больше и разнообразнее выборка (разные типы,
  разное качество фото, разный почерк заполнения), тем честнее цифра.
- Табличные типы (накладная, справочник номенклатуры) сравниваются построчно
  по порядку — если Gemini вернул строки в другом порядке или с другим
  количеством строк, сравнение по индексу может занизить точность даже
  там, где содержание верное. Для табличных типов имеет смысл сначала
  смотреть на список расхождений глазами, а не только на итоговый %.
