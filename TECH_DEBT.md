- **Согласованность ФИО между документами пачки — для переводческих бюро.**
  Ethan (7 сен 2026) спросил про полезный функционал для переводческих
  агентств. Обсудили несколько идей (готовые варианты транслитерации,
  билингва-экспорт оригинал/перевод, подсчёт объёма для расценки,
  confidence как чек-лист перед нотариальным заверением) — самой сильной и
  наименее затратной признана эта: бюро обычно переводит пакет документов
  на одного человека (паспорт + диплом + свидетельство о браке), и если
  ФИО в разных документах пачки написано по-разному — это проблема для
  нотариального перевода, которую стоит подсветить.
  - **То же поле загрузки, НЕ отдельная часть приложения** (Ethan явно
    спросил, подтверждено это решение) — проверка имеет смысл только
    внутри одной пачки одновременно, ровно как поиск дублей. Отдельный
    раздел приложения означал бы новое состояние/экран и подталкивал бы к
    хранению "дела клиента" между сессиями — это уже архив, который
    сознательно отложен (см. ниже).
  - **Явно разграничено с поиском дублей** (Ethan сформулировал сам, точно):
    поиск дублей — сравнение ВНУТРИ одного типа документа (два паспорта с
    одинаковым номером — вероятно, одна копия загружена дважды);
    согласованность ФИО — сравнение МЕЖДУ разными типами документов
    (паспорт vs договор — ФИО должно совпадать, раз это один человек).
    Технически — отдельная функция рядом с `findDuplicates`
    (`duplicateDetection.js`) или соседний модуль, не переиспользование той
    же функции с другим условием.
  - **Считать на своей стороне (JS в браузере), НЕ через промпт Gemini**
    (Ethan подтвердил после явного вопроса "на нашей стороне или промпт
    Gemini?") — тот же выбор, что и весь остальной движок бизнес-правил/
    поиска дублей: дёшево (без доп. вызовов, без риска упереться в RPM),
    быстро, детерминированно и объяснимо. Цена подхода — простое сравнение
    строк не поймает смысловую эквивалентность (инициалы "И.И." vs полное
    имя, транслитерация иероглифы/латиница) — только явные несовпадения.
    Явно обозначенный план на будущее: начать с простого сравнения (точное
    совпадение, без учёта регистра, может быть — с распознаванием
    инициалов), и только если практика покажет, что это упускает слишком
    много реальных случаев (особенно транслитерацию), рассмотреть отдельный
    редкий вызов Gemini именно для сомнительных случаев — не на каждую
    пачку целиком.
  - **Открытая развилка, ещё не решена**: как отличить "один человек с
    опечаткой/другим написанием" от "два разных человека в одной пачке по
    ошибке"? Точное совпадение строк — самый безопасный вариант (меньше

    собственно, и задумана вся идея. Решить перед началом реализации.
  - Реализация НЕ начата — это зафиксированный план после обсуждения, а не

  Excel/CSV (один заголовок, без объединённых ячеек, строка = позиция) с
  РУЧНЫМ сопоставлением колонок один раз при настройке — то есть наш
  Excel/CSV-экспорт УЖЕ структурно подходит, отдельный "1С-формат" строить
  не нужно (и Google Таблицы этим же экспортом уже покрыты — открывать чистый
  CSV/Excel умеют одинаково). Реальный найденный пробел — не файл, а состав
  колонок: у табличных типов не было разбивки по НДС, без которой документ
  нельзя корректно провести в 1С-бухгалтерию. Добавлены колонки "Ставка НДС"/

  транзакция) — читаются с документа как есть, не вычисляются моделью. См.
  `lib/docSchema.js` + синхронную копию `public/js/config/docSchema.js`,
  коммит `3b1691e` (7 сен 2026). НЕ проверено на реальных документах с
  печатным НДС (как для китайского паспорта ранее в этом файле) — стоит
